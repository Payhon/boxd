01 / DECISION

先给结论，再看分数

评分用于组织团队讨论，不替代同硬件 PoC。未通过 K8s 硬门槛的项目，即使 Browser/RPA 得分很高，也不会成为本轮直接采用建议。

01主 PoC

OpenSandbox

最接近完整 Sandbox-as-a-Service：统一生命周期 API、多语言 SDK、K8s controller、资源池、网络组件，以及 Browser/VNC/VS Code 示例位于同一项目边界。

验证重点：RuntimeClass 隔离、池化 P95、RPA 会话稳定性、升级路径
02架构对照

Agent Sandbox

Kubernetes 治理、CRD 和原生资源模型更克制可信。若团队愿意自建上层 API、控制台和 RPA 产品面，它可能是更标准、更低锁定的编排底座。

验证重点：router、warm pool、PVC、gVisor/Kata 与 Browser 镜像组合
03性能专项

Mitos

核心差异是 Firecracker live-fork：适合同一 warm state 分叉多条 Agent 探索路线。性能证据透明，但项目年轻，Browser/RPA 产品面明显不足。

验证重点：fork 密度、节点故障、snapshot 分发与路径能力差异
名称与层级校正：清单中的 “Mitosis” 本报告按当前项目 Mitos（mitos-run/mitos） 评估；“Firecracker Shim”按 firecracker-containerd 评估。Alibaba OpenSandbox 仓库当前组织名为 opensandbox-group/OpenSandbox。这三处均保留用户原意，同时按现行官方项目核验。

  • 本地镜像/快照 → 对象存储 + node cache
  • 本机网络 → CNI、egress policy、metadata block
  • 单机 lifecycle → node loss、retry、fencing
工作量判断

不是短平快路线

  • 内部 beta：约 16–24 engineer-weeks
  • 生产多租户：约 40–70 engineer-weeks
  • 另需 KVM 真机、故障注入和安全评审
  • Browser/RPA 是最值得保留的优势
建议的自研边界若采用 SmolVM，不要把它 fork 成一个巨型控制面。把它收敛为节点级 smolvm-node，控制面保持 runtime-neutral；先交付单租户、静态节点和可恢复 lifecycle，再做多租户、自动扩缩和跨节点快照。若目标是尽快上线生产 K8s，直接采用 OpenSandbox / Agent Sandbox 更经济。
06 / FOUR-WEEK POC

用同一把尺结束纸面争论

PoC 只选择 OpenSandbox、Agent Sandbox、Mitos；固定同一 Kubernetes 版本、同一裸机 KVM 节点、同一镜像、同一网络策略与同一负载脚本。

  1. W1
    部署与安全基线

    安装、升级、卸载；gVisor 与 microVM profile；metadata/私网阻断；tenant 越权、secret 泄漏、镜像供应链与未实现能力是否显式失败。

  2. W2
    Compute 与 Agent

    cold/warm TTI P50/P95/P99、首次命令、并发 1/10/100、失败清理、包安装、文件、PTY、24 小时会话与节点重启恢复。

  3. W3
    Browser 与 RPA

    Chromium ready、CDP/VNC 人工接管、断线重连、上传下载、中文字体、剪贴板、录屏、两小时 RPA 成功率和每会话带宽。

  4. W4
    成本与运维

    每节点稳定密度、warm pool 空转、镜像/快照存储、滚动升级中断、日志/指标/审计、每 1,000 sandbox-hour 的全成本。

必须量化TTI P95最大安全密度RPA 成功率恢复时间 RTO单位成本

07 / METHOD & LIMITS

证据等级与验证边界

本报告用于形成候选集和 PoC 设计，不是最终采购决策。所有结论均应在目标集群和真实业务脚本上复核。

LEVEL A

可复现实测

官方给出硬件、脚本、原始结果或可执行 benchmark。当前主要是 Mitos 的 warm-claim 与 fork 数据；仍不可跨项目直接比较不同操作口径。

LEVEL B

官方能力或自报数字

仓库/文档明确描述能力，但缺少统一硬件与完整 P50/P95。OpenSandbox、Agent Sandbox、K8E、E2B、SmolVM 多数速度信息属于这一层。

LEVEL C

工程推断或未知

从架构、依赖和现有实现推断维护成本、资源结构与集群化工作量。页面明确标出未知项，不用营销数字填空。

最终建议

先验证 OpenSandbox 能否以可接受的运维成本覆盖四类场景；若团队愿意自建产品面，Agent Sandbox 是更标准的 K8s 底座。只有当 live-fork 是核心业务优势时才押注 Mitos。SmolVM 集群化是战略自研路线，不是当前快速替代方案。

验证边界

未在同一硬件运行基准，未完成真实 K8s 生产、真机或安全渗透验证。成本估算不包含特定云价格，社区数字可能随时间变化。
